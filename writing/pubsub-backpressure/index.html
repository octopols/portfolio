Running Pub/Sub in a microservice system

Publishing is the easy half. Everything difficult about Pub/Sub lives on the subscriber side, in a lease model most teams never configure — and the defaults assume a handler far faster than yours.

[ 01 — Delivery semantics ]

What at-least-once actually costs you

Pub/Sub is at-least-once by default. Not sometimes, not only under failure — by design. A message you have already processed can arrive again, at any time, on any consumer, and the system considers that correct behaviour.

Exactly-once delivery is available as a subscription setting, and it is genuinely useful, but it is narrower than the name suggests: it applies within an acknowledgement window on a single subscription, it constrains where your subscribers can run, and it costs throughput. It also does not make your side effects safe. If your handler charges a card or sends an email, an exactly-once subscription does not save you — the crash between "sent" and "acked" still happens.

The first design decision is not which flags to set. It is accepting that every consumer you write must be safe to run twice on the same message.

Everything else in this guide assumes that. Section 07 covers how to get it. If you take one thing away, take that one — it is the difference between a queue that degrades gracefully under load and one that corrupts data whenever it is busy.

[ 02 — The lease model ]

The ack deadline is a lease, not a timeout

When a subscriber receives a message it takes out a lease on it. The ack deadline is how long that lease lasts: acknowledge within it and the message is done; miss it and Pub/Sub assumes your consumer died and hands the message to someone else.

The default is 10 seconds, and the configurable range is 10 to 600. Almost nobody's handler finishes in 10 seconds, which is why the client libraries paper over it: a lease-management thread calls modifyAckDeadline in the background, extending the lease while your handler runs, up to a maximum total extension you can also configure.

That works well, and it hides the failure mode. Lease extension renews the messages your process is holding — including the ones sitting in the client's internal buffer waiting for a worker slot that isn't free. A message can burn its entire lease without your code ever seeing it.

A lease you cannot service is worse than a message you never pulled. The second row still consumes a worker eventually — just after another consumer has already started the same work.

So derive the deadline from measurement, not taste. Take the p99 of your handler, add headroom, set that. Too short and you manufacture redeliveries for work that was going to succeed. Too long and a genuinely dead consumer holds its messages hostage for the full deadline before anyone retries them.

[ 03 — Flow control ]

Size what you hold, not what you can receive

Flow control caps how much a single subscriber client leases at once: maxOutstandingMessages and maxOutstandingBytes. These are the most consequential settings on the subscriber and the ones most often left alone. The defaults are generous — the Node client will hold a thousand messages — because they are tuned for a handler that returns in milliseconds.

A third setting matters as much and gets noticed less. allowExcessMessages lets the client accept a delivery that pushes it past your limit rather than deferring it. Left on, it quietly reintroduces the problem you just configured away. Turn it off.

Sizing it

Little's Law gives you the number. What a process can have in flight is its concurrency multiplied by how long each item takes: 

// What one process can actually be working on at once.
in_flight = worker_concurrency × p99_handler_seconds

// Lease a little more than that, so workers never starve —
// but not so much that the surplus ages out of its lease.
maxOutstandingMessages ≈ in_flight × 1.5

The multiplier is a buffer, not an ambition. Much above 2× you are holding messages whose leases will expire before a worker reaches them, and you have rebuilt the failure from section 02 with extra steps.

Rule of thumb

Never lease what you cannot finish inside the deadline. A message left in the broker is a message another consumer can take. A message buffered in your client is a message nobody can take — and it is ageing.

[ 04 — Backpressure ]

The slowest dependency should set the pace

Flow control bounds what the client holds. It says nothing about what your handler does with it. If the handler spawns unbounded concurrent work — a database write, an HTTP call to a service with its own limits — the puller happily accepts messages the downstream cannot absorb, and the lease clock starts on all of them at once.

In a microservice system this is the normal case, not the exception. The consumer is rarely the bottleneck. It is a thin thing in front of a database, a third-party API, or another service with its own capacity and its own opinion about how fast you may go. 

// Bound in-flight handler work so the downstream sets the rate.
const limit = pLimit(DOWNSTREAM_CONCURRENCY);

subscription.on("message", (msg) =>
  limit(() => handle(msg)),
);

With both bounds in place, the queue is finally allowed to do the job a queue exists for: hold work. Backlog depth becomes a signal about arrival rate rather than a symptom of your own consumers misbehaving — which is what makes section 06 possible at all.

[ 05 — Redelivery amplification ]

Why adding consumers can make a backlog worse

This is the part that surprises people, so it is worth doing carefully.

Redelivered work is indistinguishable from new work. It takes a pull slot, a worker, a database round-trip, and at the end of it the result may be redundant. So the throughput that actually clears the backlog is not the throughput you are paying for: 

useful_throughput = raw_throughput / (1 + redelivery_rate)

Be precise about what this does and does not explain, because the obvious reading is wrong. If the redelivery rate r were a constant — a fixed tax per message, independent of fleet size — then useful throughput would be n · k / (1 + r), which still grows linearly in n. A constant redelivery rate is not futility. It is a discount. Scale-out would be wasteful, and it would still work.

The failure case is when r rises with n, and in a microservice system there is an obvious reason it would: every consumer calls the same downstream. Add consumers, concurrency against that shared dependency rises, its latency rises with it, and handler time rises in turn. Handler time is exactly what the ack deadline is racing. Each node you add pushes a few more messages on every other node past their deadline.

The diagnostic

One ratio separates the two cases, and total throughput hides it completely, because total throughput goes up either way:

Plot this before you provision

Acked messages per node per minute, against fleet size. Flat means you are genuinely under-provisioned and scale-out is the right answer. Sloping down means the nodes are interfering through something they share — stop adding them and go find it.

Where I hit this

Two subscriptions on a delivery path at work, carrying 1.26M messages of combined backlog, with worst-case delivery delay at 2.4 hours. The standing response had been consumers — 38 of them, on an autoscaler that rarely scaled back down. Fixing flow control, ack deadlines and backpressure took the backlog under 4K and worst-case delay to 94 seconds, and the whole scale-out was retired. No capacity was added. The capacity had been there, being spent twice.

[ 06 — Autoscaling ]

Pick a signal that isn't polluted by your own output

The obvious metric to scale a subscriber fleet on is num_undelivered_messages — backlog depth. It is the standard choice and it is fine when the backlog is exogenous.

It is a trap when it isn't. A redelivered message is undelivered again, so every duplicate your fleet generates is counted straight back to the autoscaler as fresh demand. If your consumers are missing deadlines, the number on the dashboard is not queue depth — it is queue depth plus your fleet's own churn. Scaling up raises the churn, which raises the metric, which authorises scaling up.

It also explains a symptom that otherwise looks like a bug in the autoscaler: a fleet in this state can never scale down. Shrinking would reduce the churn inflating the metric, but the metric has to fall first for shrinking to be permitted.

The last row is the one people skip. If the constraint is a rate-limited third-party API, no number of consumers changes your throughput. Scaling on backlog will happily spend money proving that.

[ 07 — Correctness ]

Idempotency, ordering and dead letters

Idempotency

The cheapest version: give every message a stable business key, record the keys you have completed, and check before acting. Not the Pub/Sub messageId — a redelivery of the same logical event after a publisher retry gets a new one. Use something from the payload that identifies the work: an order id, an invoice period, a state transition.

Some handlers are naturally idempotent — SET status = 'shipped' can run all day. Most are not, and the ones that aren't tend to be the ones that spend money. Write the dedup table.

Ordering keys, and what they cost

Ordering keys guarantee that messages sharing a key are delivered in order. They also serialise them: one key is processed by one subscriber at a time, so your parallelism is bounded by your number of distinct keys, and one slow message blocks everything behind it on that key.

Use them where order is genuinely part of correctness, key as narrowly as you can — per entity, never per tenant — and expect throughput to look nothing like the unordered case.

Dead letters

Configure a dead-letter topic with maxDeliveryAttempts. Without one, a message your handler cannot process is immortal: it fails, it is redelivered, it fails again, forever, consuming a lease and a worker each time. A single poison message with a large payload can hold a meaningful fraction of a subscriber's capacity indefinitely.

Also worth doing

Alert on the dead-letter topic having anything in it at all. A dead-letter queue nobody reads is a folder where you keep your outages.

[ 08 — Reference ]

A starting configuration

Not universal values — nothing here is. This is the set of decisions worth making deliberately, with the reasoning attached, so you can derive your own. 

const subscription = pubsub.subscription(name, {
  flowControl: {
    // concurrency × p99 handler seconds × 1.5
    maxOutstandingMessages: 120,
    // from your payload profile, not the default
    maxOutstandingBytes: 64 * 1024 * 1024,
    // defer rather than over-accept
    allowExcessMessages: false,
  },
  // measured p99 + headroom, not the 10s default
  ackDeadline: 60,
});

// The downstream sets the pace, not the puller.
const limit = pLimit(DOWNSTREAM_CONCURRENCY);
subscription.on("message", (msg) => limit(() => handle(msg)));

The thread running through all of it: every one of these settings limits how much work the system admits at once. None of them make it faster. That is usually the point — throughput problems in a queue are more often about work being done twice than about there being too little capacity to do it once.

A queue that grows while you add consumers is not telling you about capacity. It is telling you that some of your capacity is being spent twice.
