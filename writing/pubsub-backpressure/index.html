What 38 nodes were hiding

Two subscriptions carrying 1.26M messages of backlog, a worst-case delivery delay of 2.4 hours, and a fleet that had been sized to absorb it. The fleet was not undersized. It was feeding the backlog.

[ 01 — The symptom ]

A queue that would not drain, and a fleet that would not shrink

Two Pub/Sub subscriptions on the delivery path. Combined backlog sat at 1.26M messages. Worst-case delivery delay — the age of the oldest unacked message — reached 2.4 hours.

The response, over time, had been consumers. The fleet had grown to 38 nodes, autoscaled on backlog depth, and it frequently never scaled back down. That last detail is the interesting one, and it took me a while to see why.

The system was not alerting on anything except the backlog itself. Nothing was crashing, error rates were normal, and every individual node looked healthy. It read as a capacity problem, and it had been treated as one for months.

[ 02 — The tell ]

Throughput per node fell as nodes were added

Adding consumers did something. Each scale-out event produced a visible dip in backlog, which is exactly what you would expect if the fleet were undersized — and exactly why the approach kept getting repeated.

But the dip never held, and the number that mattered was moving the wrong way: messages successfully acked per node per minute was falling as the fleet grew.

That is not a capacity curve. A fleet that is genuinely too small shows roughly flat per-node throughput as you add nodes — you get more total work done and the per-node rate stays put. Per-node throughput that degrades with fleet size means the nodes are interfering with each other, or they are doing work that does not count.

They were doing work that did not count.

[ 03 — The mechanism ]

Redelivery amplification

Pub/Sub is at-least-once. Every message you pull comes with an ack deadline — a lease. Ack within the deadline and the message is done. Miss it, and Pub/Sub assumes the consumer died and redelivers the message to someone else.

The client library tries to protect you from this: a lease-management thread extends the deadline in the background with modifyAckDeadline while your handler is still running. That works right up until the process has leased more messages than it can actually work through — at which point messages sit in the client's internal buffer, holding leases, waiting for a worker slot that is not coming fast enough.

A lease you cannot service is worse than a message you never pulled. The second row still consumes a worker eventually — it just does so after another node has already started the same work.

Redelivered work is indistinguishable from new work. It consumes a pull slot, a worker, a database round-trip and a downstream call, and at the end of it the message may well be redundant. So the useful throughput of the fleet is not the raw throughput: 

useful_throughput = raw_throughput / (1 + redelivery_rate)

And here is the part that makes the scale-out futile: adding nodes scales both terms. More consumers pull more messages, lease more than they can finish, and miss more deadlines — in proportion. The redelivery rate is roughly invariant to fleet size, because it is set by the relationship between handler latency and lease capacity per process, not by how many processes there are.

The ratio never improves. You are buying capacity and duplicate work in a fixed proportion. Tripling the fleet triples both — which is why the backlog kept re-converging after every scale-out.

[ 04 — Why it never scaled down ]

The autoscaler was closing the loop

The fleet scaled on num_undelivered_messages — backlog depth. That metric is the standard choice and it is fine when the backlog is exogenous. Here it was not.

The 38 nodes were not responding to load. They were responding to themselves. Every node added made the signal it was scaling on slightly worse, which is why the fleet ratcheted up and stayed there.

Worth knowing

num_undelivered_messages counts redeliveries. oldest_unacked_message_age is the better autoscaling signal for exactly this reason — it tracks whether you are actually falling behind, not how much traffic is circulating. A control loop whose input is polluted by its own output is not a control loop.

[ 05 — The fix ]

Three changes, all of them about admitting less work

None of this was solved by making the handler faster. It was solved by making each process honest about how much work it could hold.

1. Flow control sized to what one process can finish

maxOutstandingMessages and maxOutstandingBytes cap how much the client leases at once. The defaults are generous — they assume your handler is fast. Sized correctly, they mean a process never holds a lease it cannot service inside the deadline.

allowExcessMessages: false matters here. Left at the default, the client will accept a delivery that pushes it past the limit rather than deferring it, which quietly reintroduces the problem you just configured away.

2. An ack deadline derived from measured latency

The deadline should come from the handler's actual p99, with headroom — not from a default, and not from a guess. Too short and you manufacture redeliveries for work that was going to succeed. Too long and genuine failures sit undetected for the full deadline before anyone retries them.

3. Backpressure from the real bottleneck

The constraint was never the puller. It was what the handler called downstream. Without a bound on in-flight handler work, the puller cheerfully accepts messages the downstream cannot absorb, and the lease clock starts on all of them at once.

Bounding concurrency inside the handler lets the slowest dependency set the pace of the whole consumer. The queue is then allowed to do the job a queue is for — holding work — with the depth of it as a signal rather than a symptom. 

// Lease only what this process can finish inside the deadline.
const subscription = pubsub.subscription(name, {
  flowControl: {
    maxOutstandingMessages: /* sized from p99 handler latency × worker count */,
    maxOutstandingBytes:    /* sized from payload profile, not left at default */,
    allowExcessMessages:    false,   // defer, don't over-accept
  },
  ackDeadline: /* measured p99 + headroom */,
});

// The downstream sets the pace, not the puller.
const limit = pLimit(/* what the slowest dependency sustains */);
subscription.on("message", (msg) => limit(() => handle(msg)));
The general shape

All three changes reduce how much work the system accepts at once. None of them increase how much work it can do. The throughput went up anyway — because the capacity had been there the whole time, spent twice.

The 38 nodes were retired. Not reduced — retired. The original fleet handled the same traffic once it stopped competing with itself, which is the clearest evidence available that the extra capacity had never been doing anything except generating the load that justified it.

[ 07 — What generalises ]

Scale-out is a valid answer to the wrong question

The uncomfortable part of this one is that adding nodes worked, briefly, every single time. There was always a dip. The feedback was positive, immediate, and completely misleading, and it is why the workaround survived long enough to become the architecture.

A queue that grows while you add consumers is not telling you about capacity. It is telling you that some of your capacity is being spent twice.

The diagnostic that would have caught this in an afternoon is one ratio: acked messages per node, plotted against fleet size. If it slopes down, stop provisioning and go find the duplicate work. Total throughput hides this completely — it goes up either way.
