envswitch

Switch shell environments with a single command. No binaries, no hooks to approve, no .env files in your repos.

[ 01 — What it does ]

Type the environment name. That's the whole interface.

$ staging
 ✓ Loaded staging  (5 vars)

$ production
 ! Load production env? (y/n): y
 ✓ Loaded production  (12 vars)

$ unsetenv
 ✓ Cleared production environment

Env files live in ~/.envs/, one file per environment, outside every repository. Each file automatically becomes a shell command — drop in production.env and production is now a command. There is no registry to update and no config to edit, because the filename is the configuration.

[ 02 — The monorepo problem ]

One repo, many services, one shell.

The problem this was actually built for: a monorepo where the environment you need depends on which part of the tree you're in and which branch you're on. Directory alone isn't enough — growth/feature-x and payments/new-api live in the same checkout and want different credentials.

So env files carry tags in their header, and the shell resolves them on cd and on branch switch: 

# ~/.envs/growth_staging.env
# dir: ~/monorepo
# branch: growth/*
API_KEY=sk-staging-123
$ cd ~/monorepo                    # on branch growth/feature-x
 ✓ Auto-loaded growth_staging  (dir:~/monorepo, branch:growth/feature-x)

$ production                       # context-aware: resolves to growth_production
 › Context: growth
 ✓ Loaded growth_production  (5 vars)

$ git switch payments/new-api
 ✓ Auto-loaded payments_staging  (branch:payments/new-api)

$ cd ~/Desktop
 ✓ Left mapped directory, clearing payments_staging

The last line is the one that matters most. Leaving the directory unloads the environment rather than leaving it resident — so a shell that has wandered out of the monorepo is not still holding credentials for it.

[ 03 — The design rule ]

Only tag your safe defaults.

Tagged environments auto-load. Production is never tagged. It is reached deliberately — by name, or through context resolution — and it can be marked protected so loading it requires a typed confirmation.

This is the whole safety model, and it is deliberately not clever. Anything that can happen implicitly — on a cd, on a branch switch, without you asking — is restricted to environments where being wrong is cheap. Everything expensive requires an explicit act.

The alternative designs all fail the same way: if production can auto-load, then some sequence of git switch and cd silently arms a shell with production credentials, and you will find out which sequence at the worst possible moment.

[ 04 — Cost ]

It runs on every prompt, so it has to be free.

Auto-loading means hooking directory and branch changes, which means this code runs constantly. The resolution is tiered so the common cases cost nothing:

No directory tags

Zero overhead. Nothing to match, nothing to check.

Directory match, no branch tags

Resolved without invoking git at all.

Branch disambiguation needed

Git is read once (~1ms), and the result is cached.

Shelling out to git rev-parse on every prompt is the standard way tools like this become the reason your terminal feels slow. Reading git only when the answer actually depends on the branch keeps it off the hot path for everyone who isn't using that feature.

[ 05 — Against the alternatives ]

Why not direnv.

envswitch direnv dotenv aws-vault
Scope Whole shell Per directory Per app (runtime) AWS creds only
staging → prod production Edit .envrc + reload Restart app aws-vault exec prod
Monorepo + branches Auto-load by dir + branch pattern One file per dir, no branch awareness N/A N/A
Files in repo No — everything in ~/.envs Yes — .envrc in each project Yes — .env in project root No
Install Source one file Binary + shell hook + allow per dir Language-specific package Binary + keychain setup
Prod protection Built-in confirmation None None Session-based
Config to add one None — add a file, get a command Edit + direnv allow Edit app config Edit ~/.aws/config

direnv is the closest tool and it is a good one — but it is directory-scoped and repo-resident by design. It answers "what does this folder need", and it puts a file in the folder to say so. In a monorepo those are the two properties you don't want: one folder, many answers, and no secrets checked in.
